# TinyStories 50M context comparison

Question: does another 100,003,840 supervised targets at training context 512 improve development loss or diagnostic continuations compared with context 256?

Both arms promote weights from the verified final 50M BF16 checkpoint `c72d7d0283de2c6008f1b80d855bad6cb6ebc497f0094957a8982bd58a049110` using native `train --promote`. They start fresh AdamW moments, RNG, cursor, schedule and zero counters. Each uses 24,415 updates / 100,003,840 additional targets, seed 42, BF16, reference attention, the same 50,556,800 parameters, tokenizer and prepared corpus. AdamW peak 0.0006, floor 0.00006 and 2,048 warmup updates are identical. The only treatment changes are sequence length and compensating microbatch: 256 x 8 x 2 versus 512 x 4 x 2, both 4,096 targets/update. The parent's architecture already has max_seq_len 512; no positional or weight resizing is requested.

Lab pin: `903ad2f0bb261935132dee53295aba6b66f8e792` (current main inspected before execution). Bind physical paths through native `config derive`; publish configuration-specific prepared-input bundles while reusing the existing snapshot, tokenizer and packed arrays. No reacquisition or tokenizer fitting is part of this iteration. Each scientific arm must run on the same device/runtime. Do not interpret different hardware as a context effect.

The frozen [evaluation protocol](evaluation-protocol.json) scores both final checkpoints at context 256 and 512 on the same first 65,536 validation target positions, with fixed batch sizes. Bind only the exact checkpoint digest and physical prepared location when materializing the native `eval --panel` declarations. Run both panels on the parent before training and both children after completion. Inline validation differs by training context and is operational evidence, not the paired score. This is an already-used development selection, not an untouched final test set.

The frozen [generation protocol](generation-protocol.json) retains the original 12 prompts and adds four prompts longer than 256 tokens. Reuse the parent's existing 24 short outputs for the exact final checkpoint; generate its eight new long outputs before training. Each child receives all 32. No prompt tuning after output inspection.

Before full arms, perform a separate bounded 256-update calibration for each shape using the same promotion parent and full arm horizon. Profile these disposable commands with Python cProfile; profiled timing is excluded from scientific throughput. Check finite loss, overflow, memory, verified checkpoints and exact promoted step-zero weights/state. Profile reporting/checkpoint call counts and inspect growth against retained operational history. Do not change engine code under an active run. Full arms stop after step 256 once, verify state and resume unchanged to their original horizon; those initial updates count in the arm budget.

Interpretation limits: one seed, an additional-training comparison with reset optimizer/cursor, different sequence block boundaries and shuffled block order, reused development data, and assistant-reviewed diagnostic prompts. Equal target counts do not mean identical ordered token exposure across sequence lengths. No model-quality or cross-device equivalence claim follows from successful execution.

Hardware allocation is operational: prefer the existing Intel GPU for the controlled pair after native handoff and measured fit, with ROCm for profiling. If that path is unavailable, keep both scientific arms on ROCm and record the constraint; never split the pair across devices. No paid services or installations are required by these declarations.

[ROCm profiling](rocm-profile.json) records separate 256-update promoted calibrations, not scientific arm results. At context 512, 570 file/directory fsync calls consumed 6.41 seconds across the command; 290 SQLite commits consumed 2.01 seconds. Progress publication ran 266 times and metric logging 258 times. Progress serializes the full stage history on each update: a separate 20-repeat serialization-only sample grew from about 0.03 ms at 10 records to 5.96 ms at 2,150 records. These overlapping costs identify concrete optimization candidates, but do not account for every second of the earlier long run. A durable bounded progress snapshot and append-oriented history merit a generic Lab change with crash-recovery checks; no engine patch was applied to these experiments.

[Intel portability and calibration evidence](intel-portability.json) records successful native transfer, content-addressed reuse and a separate 256-update promoted calibration at about 5,284 optimizer targets/s, 2.48 GB peak reserved device memory and zero overflow retries. Both frozen parent panels completed on the identical-weight step-zero replica; matched FP32 losses agree with ROCm within 1.5e-8. The parent scores about 1.075 at context 256 and 1.934 at context 512. These different contexts must not be mistaken for a hardware discrepancy.

None reliably completes the stated key-location, promised-recipient, damaged-boat or remaining-apple detail; this is an assistant diagnostic observation, not independent scoring. The original short parent panel remains the prior ROCm panel, so parent short-versus-long comparisons also differ in device.

Diagnostics therefore used a verified identical-weight native step-zero replica. Direct promotion also required native tokenizer/output path binding before staged inputs were applied; its first launch failed before run creation. These failures are preserved in the evidence. No custom metadata rewriting, re-tokenization, dependency installation or host security changes were used. Colab and unified topology placement remain unverified.

## Completed Intel context comparison

[Completion and resource evidence](intel-context-results.json) verifies both arms at exactly 24,415 unique, contiguous updates / 100,003,840 supervised targets, with zero overflow retries across all updates and valid full-state final checkpoints. Both matched the original parent weights at step zero, started fresh optimizer/cursor/schedule state, stopped at step 256, and resumed with exact state equality. Original checkpoints remain intact.

| Training checkpoint | Eval context 256 | Eval context 512 |
| --- | ---: | ---: |
| Original parent, identical-weight Intel replica | 1.075286 | 1.933697 |
| 256-context child | 1.088874 | 1.649023 |
| 512-context child | 1.090444 | 1.026256 |

Each panel uses the same 65,536 target positions and matching native comparison groups across checkpoints. The 512 child greatly improves the longer-context panel; short-context losses are close, slightly favoring the 256 child, and both are slightly worse than the original parent there. This is one seed on reused development data, not proof of general quality improvement.

All [32 outputs from the 256 child](generation-256.json) and [32 from the 512 child](generation-512.json) are retained. Neither child reliably supplies any of the four long-prompt facts in either decoding mode. The 512 child preserves the ball location and some name/sharing details in short prompts, but still produces repetition, object confusion, implausible repairs and unresolved problems. For example, its seed story can turn the pot itself into a plant, and one watering story loops the same warning. These are provisional assistant observations. The current context-panel CLI does not expose exact completion-token counts or stop reasons, so an unfinished ending is not automatically an EOS failure.

Complete training-command time, summed across initial and resumed segments, was 21,479.46 seconds (5h 57m 59s) for 256 and 22,223.61 seconds (6h 10m 24s) for 512. Optimizer-only throughput was 5,356 versus 5,215 targets/s; peak reserved device memory was 2.19 versus 2.51 GB. The resumed invocations recorded 1,981.91/2,113.56 seconds of reporting and 301.03/313.23 seconds of checkpoint work, respectively; these phase figures exclude the initial 256-update invocation. Shared-host samples recorded no node-pressure or readiness failures and no training-process swap. Sampling does not prove zero impact on other services.
