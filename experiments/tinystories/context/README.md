# TinyStories 50M context comparison

Question: after another 100,003,840 supervised targets, does training at context 512 give better development loss or better continuations than training at context 256?

Both arms take their weights from the verified final 50M BF16 checkpoint `c72d7d0283de2c6008f1b80d855bad6cb6ebc497f0094957a8982bd58a049110` with native `train --promote`. They start with fresh AdamW moments, RNG, cursor and schedule, and zeroed counters. Each uses 24,415 updates / 100,003,840 additional targets, seed 42, BF16, reference attention, the same 50,556,800 parameters, tokenizer and prepared corpus. AdamW peak 0.0006, floor 0.00006 and 2,048 warmup updates are identical. The only differences are sequence length and the microbatch that offsets it: 256 x 8 x 2 versus 512 x 4 x 2, both 4,096 targets/update. The parent already has max_seq_len 512, so no positions or weights need resizing.

Lab pin: `903ad2f0bb261935132dee53295aba6b66f8e792` (current main, checked before the runs). Set physical paths with native `config derive`, and publish a prepared-input bundle for each config while reusing the existing snapshot, tokenizer and packed arrays. Don't download the corpus again or refit the tokenizer. Run both training arms on the same device and runtime, so a hardware difference can't pass for a context effect.

The frozen [evaluation protocol](evaluation-protocol.json) scores both final checkpoints at context 256 and 512 on the same first 65,536 validation target positions, with fixed batch sizes. When you fill in the native `eval --panel` configs, set only the exact checkpoint digest and the physical location of the prepared data. Run both panels on the parent before training and on both children afterward. Inline validation differs with training context, so use it to watch training and use the panels for the comparison. This validation selection has been used before; treat it as development data.

The frozen [generation protocol](generation-protocol.json) retains the original 12 prompts and adds four prompts longer than 256 tokens. Generate greedy and temperature-0.7/top-k-40 continuations, seed 42, strict 512 context and at most 192 new tokens. Keep every output, including errors, truncation and repetition. For the parent, reuse the existing 24 short outputs from the exact final checkpoint and generate the eight new long ones before training. Each child gets all 32. Don't tune prompts after reading outputs.

Before the full arms, run a separate 256-update calibration for each shape, using the same parent and the full arm horizon. Profile these throwaway commands with Python cProfile, and leave profiled timings out of the throughput numbers. Check for finite loss, overflow, memory, verified checkpoints, and promoted weights and state that match exactly at step zero. Count reporting and checkpoint calls and see how their cost grows with the saved run history. Don't change engine code while a run is active. The full arms stop once after step 256, verify state and resume unchanged to their original horizon; those first updates count toward the arm's budget.

Limits: one seed; extra training on top of a parent with the optimizer and cursor reset; different block boundaries and shuffled block order between the two lengths; reused development data; and prompts reviewed by an assistant. Equal target counts don't mean the two arms saw the same tokens in the same order. A clean run tells you the workflow worked, not that the model got better or that devices are interchangeable.

Hardware plan: once the native handoff works and the fit is measured, run the matched pair on the existing Intel GPU and use ROCm for profiling. If the Intel GPU isn't available, run both arms on ROCm and note why; never split the pair across devices. These configs need no paid services or installs.

The Intel configs are `run-256-xpu.json` and `run-512-xpu.json`; they differ from the matching ROCm recipes only in experiment name and backend. The existing XPU runtime on the Arc A380 passed native 512-context smoke and warmup. Before the real training, run a separate promoted calibration and score the frozen parent panels. Both arms use the same device and runtime.

[ROCm profiling](rocm-profile.json) covers only the separate 256-update promoted calibrations. At context 512, 570 file/directory fsync calls consumed 6.41 seconds across the command; 290 SQLite commits consumed 2.01 seconds. Progress publication ran 266 times and metric logging 258 times. Progress serializes the full stage history on each update: a separate 20-repeat serialization-only sample grew from about 0.03 ms at 10 records to 5.96 ms at 2,150 records. These costs overlap and point at specific things to optimize, though they don't explain every second of the earlier long run. A bounded, durable progress snapshot with an append-only history would be worth a general Lab change, tested for crash recovery. We did not patch the engine for these experiments.

[Intel portability and calibration results](intel-portability.json) show that the native transfer and content-addressed reuse worked. A separate 256-update promoted calibration ran at about 5,284 optimizer targets/s with 2.48 GB peak reserved device memory and zero overflow retries. Both frozen parent panels ran on a step-zero copy with identical weights, and the FP32 losses match ROCm within 1.5e-8. The parent scores about 1.075 at context 256 and 1.934 at context 512; that gap comes from the context length, not the hardware.

[All eight parent long-context outputs](parent-generation-long.json) are kept. In an assistant's reading, none reliably gets the key's location, the promised recipient, the damaged boat or the remaining apple right. The parent's short panel is still the earlier ROCm one, so its short and long outputs also come from different devices.

The handoff works but doesn't yet hide where things are placed. Promotion through native dispatch works, but standalone inference on the minimal set of parent files failed because a data artifact was missing. So for the diagnostics we used a verified step-zero copy with identical weights. Direct promotion also needed the tokenizer and output paths set before the staged inputs were applied; its first launch failed before creating a run. Both failures are kept in the records. We did not rewrite metadata by hand, retokenize, install dependencies or change host security. Colab and unified placement across machines are still untested.

The separate ROCm performance configs `perf-512-bf16-reference.json` and `perf-512-bf16-sdpa.json` compare supported attention implementations at context 512, BF16 and 4,096 targets/update. Both start fresh with seed 42 and keep the 24,415-update schedule, stopping after 256 actual updates; compare updates 17–256 and record startup separately. They start from scratch because Lab treats the attention implementation as part of the architecture, so a checkpoint can't be promoted or resumed across it. Check that the initial weight files match, losses are finite, and overflow counters and memory look right before reading the throughput. This short calibration doesn't start a full SDPA experiment or change either Intel arm. No profiler runs during these timed runs.

The [attention performance comparison](rocm-attention-performance.json) has all four 256-update runs in A-B-B-A order: reporting time varied in the first pair, so we repeated it in reverse order. Initial weight hashes matched, all losses stayed finite, overflow retries were zero and all final full-state checkpoints verified. Aggregate updates-17–256 throughput was 44,450 targets/s for reference attention versus 53,720 for SDPA (20.9% higher); peak reserved memory was 2.68 versus 2.05 GB (23.3% lower). Mean whole-command time was 50.68 versus 49.27 seconds, from only two samples each with varying reporting and startup costs. SDPA looks promising for the optimizer step; a full run would be needed to see whether it speeds up a whole run or changes quality. The native optimizer timer synchronizes the device before reading the clock. Neither training arm used SDPA, and this comparison has no further performance runs.

## Completed Intel context comparison

The [completion and resource records](intel-context-results.json) show both arms ran exactly 24,415 unique, contiguous updates / 100,003,840 supervised targets, with zero overflow retries and valid full-state final checkpoints. Both matched the original parent weights at step zero, started with fresh optimizer, cursor and schedule state, stopped at step 256, and resumed with the state matching exactly. The original checkpoints are untouched.

| Training checkpoint | Eval context 256 | Eval context 512 |
| --- | ---: | ---: |
| Original parent, identical-weight Intel replica | 1.075286 | 1.933697 |
| 256-context child | 1.088874 | 1.649023 |
| 512-context child | 1.090444 | 1.026256 |

Each panel uses the same 65,536 target positions and the same native comparison group for every checkpoint. The 512 child is much better on the longer-context panel. On the short-context panel the two children are close, the 256 child slightly ahead, and both slightly worse than the original parent. This is one seed on reused development data.

All [32 outputs from the 256 child](generation-256.json) and [32 from the 512 child](generation-512.json) are kept. Neither child reliably supplies any of the four long-prompt facts in either decoding mode. The 512 child preserves the ball location and some name/sharing details in short prompts, but still produces repetition, object confusion, implausible repairs and unresolved problems. For example, its seed story can turn the pot itself into a plant, and one watering story loops the same warning. These are an assistant's notes. The context-panel CLI doesn't report exact completion-token counts or stop reasons, so an unfinished ending may just have hit the token limit.

Complete training-command time, summed across initial and resumed segments, was 21,479.46 seconds (5h 57m 59s) for 256 and 22,223.61 seconds (6h 10m 24s) for 512. Optimizer-only throughput was 5,356 versus 5,215 targets/s; peak reserved device memory was 2.19 versus 2.51 GB. The resumed invocations recorded 1,981.91/2,113.56 seconds of reporting and 301.03/313.23 seconds of checkpoint work, respectively; these phase figures exclude the initial 256-update invocation. Samples on the shared host showed no node pressure, no readiness failures and no swap by the training process; sampling could miss brief effects on other services.

The [learning-rate comparison](../learning-rate/README.md) that came next uses context 512 for its better long-context behavior, and keeps the original 50M parent, model and data. It starts from that parent rather than from either context child; longer context helped on the long panel but did not fix coherence.
